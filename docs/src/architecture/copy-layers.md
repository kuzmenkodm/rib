# Построение COPY-слоёв

Каждый `--copy` (или каждый элемент `copies` в `[package.metadata.rib]`)
превращается в отдельный слой image. Слои не смешиваются в один общий
tar-архив — так их можно строить независимо друг от друга, гарантированно
сохранять порядок, который вы указали, и переиспользовать в registry те
слои, что не изменились с прошлой сборки (у них будет тот же digest).

## Синтаксис

```text
<src>:<dst>[,key=value,...]
```

Примеры:

```bash
--copy ./server:/app/server,mode=0755
--copy ./config:/etc/server/,chown=1000:1000
--copy 'target/release/*.so:/usr/local/lib/'
```

Поддерживаемые опции после `dst`:

- `mode=0755` (алиас `chmod=0755`) —
  права доступа к файлу в восьмеричной записи;
- `chown=1000:1000` (или `owner=1000:1000`) — владелец `uid:gid`;
- можно указать только uid без gid — тогда gid станет `0`.

Имена пользователя и группы не разрешаются через `/etc/passwd` хост-системы.
В tar-заголовки записываются только явно указанные числовые uid/gid.

## Как разрешаются источник и назначение

`src` может быть glob-шаблоном (`*.so`, `target/release/lib*.so`) — он
раскрывается непосредственно во время сборки, а не сразу при разборе флага.
При построении слоя `rib`:

1. раскрывает glob и сортирует совпадения (для воспроизводимого порядка);
2. проверяет, что источник существует;
3. принимает только обычные файлы и каталоги — символические ссылки и
   специальные файлы (устройства, сокеты и т.п.) отклоняются с ошибкой;
4. вычисляет итоговый путь внутри image;
5. обходит содержимое каталогов в отсортированном порядке;
6. добавляет недостающие родительские каталоги как отдельные записи в tar.

Правила для `dst` копируют логику `COPY` в Dockerfile, которая знакома
многим пользователям Docker:

- файл → путь без завершающего `/` — итоговое имя внутри image берётся
  ровно таким, как вы написали;
- файл → путь с завершающим `/` — `dst` считается каталогом, и файл кладётся
  внутрь под своим исходным именем;
- каталог как источник — в image попадает *содержимое* этого каталога, а не
  сам каталог как вложенная папка;
- если glob раскрылся в несколько файлов, `dst` обязан заканчиваться на `/`
  — иначе назначение нескольких файлов неоднозначно и сборка завершится
  ошибкой;
- пути внутри tar никогда не начинаются с `/` (так требует формат tar для
  образов);
- компоненты пути `.` и `..`, пустые компоненты и NUL-байты в `dst`
  запрещены — это защита от случайного (или намеренного) выхода за пределы
  предполагаемого каталога.

Если вы используете glob, обязательно берите шаблон в кавычки — иначе его
раскроет ваш shell ещё до того, как аргументы дойдут до `rib`:

```bash
rib build ... --copy 'target/release/*.so:/usr/local/lib/'
```

## Как получается детерминированный tar-файл

Детерминированность означает, что повторные запуски `rib` с одним набором
входных файлов формируют побайтово одинаковый слой и одинаковый digest.
Стандартный `tar` сохраняет время модификации, может использовать различный
порядок обхода каталогов и не нормализует права доступа. `rib` устраняет эти
источники неопределённости:

- обход каталогов и результаты glob всегда сортируются;
- `mtime` (время модификации) у каждой записи всегда `0`;
- uid/gid по умолчанию — `0` (если явно не указан `chown`);
- имя пользователя/группы в заголовке всегда пустое;
- права каталога по умолчанию — `0755`;
- права обычного файла по умолчанию — `0755`, если исходный файл исполняемый
  на Unix, иначе `0644`;
- явный `mode` переопределяет права обычных файлов; каталоги всегда получают
  `0755`. Явный `chown` применяется к файлам и каталогам;
- используются заголовки формата GNU tar — в том числе для путей длиннее
  100/255 символов, которые классический формат tar не поддерживает.

Любые метаданные файловой системы, не перечисленные в этом списке (например,
extended attributes), в слой не переносятся осознанно,
потому что такая функциональность обычно не нужна внутри контейнера и мешала бы
воспроизводимости.

## Один проход по данным — сразу и хеш, и сжатие

Пока `rib` пишет несжатый tar, он одновременно и хеширует его, и подаёт в
gzip — то есть исходные файлы читаются с диска только один раз, независимо
от того, сколько разных идентификаторов в итоге нужно получить:

```text
исходные файлы
    │
    ▼
tar::Builder
    │
    │ байты несжатого tar
    │
    ▼
CancellableWriter          (проверяет флаг отмены на каждой записи)
    │
    ▼
SplitWriter                (раздаёт один и тот же поток в две стороны)
    ├──► HashingWriter ──► опционально: layer.tar
    │       └── diff_id + uncompressed_size
    │
    └──► GzEncoder
             │ сжатые байты
             ▼
          HashingWriter<File> ──► layer.tar.gz
             └── digest + compressed_size
```

`HashingWriter` передаёт байты далее, одновременно обновляя SHA-256 и счётчик
размера. `diff_id` и `digest` (см. главу "Модель OCI-образа")
вычисляются за один проход по данным.

Несжатый `layer.tar` сохраняется на диск только при наличии Docker archive
среди целей публикации (этому формату требуется несжатый слой; см. главу про
registry и форматы архивов). В остальных случаях несжатый поток после
хеширования не сохраняется: `diff_id` вычисляется потоково.

Результат представлен структурой `Layer`:

```text
Layer {
    diff_id,
    descriptor,                   // media type + digest + размер сжатых байт
    uncompressed_size,
    storage: Arc<LayerStorage>,   // где на диске лежат временные файлы
}
```

## Параллельная сборка не портит порядок

Все `--copy`-директивы добавляются в общий пул задач (`JoinSet`), а семафор
ограничивает, сколько из них может работать одновременно — этим числом
управляет флаг `--jobs`. Сама gzip-компрессия и обход файловой системы —
тяжёлая по CPU и диску работа, поэтому она выполняется не на потоках Tokio, а
на отдельном пуле.

То, в каком порядке задачи реально завершились, никак не влияет на порядок
слоёв в итоговом image:

```text
COPY #1 ───────────────► результат #1 ─┐
COPY #2 ─────► результат #2            ├──► [#1, #2, #3]
COPY #3 ─────────► результат #3 ───────┘
```

Координатор собирает результаты в исходном порядке ваших `--copy`, а не в
порядке завершения. Это важно и с практической стороны: если два разных
`--copy` запишут один и тот же путь внутри image, "победит" содержимое из
той директивы, что была указана позже в командной строке — точно так же, как
более поздний `COPY` в Dockerfile переопределяет более ранний.

## Сколько это занимает места на диске

Для каждого нового слоя всегда нужен как минимум один временный файл — сжатый
blob (`layer.tar.gz`). Дополнительный несжатый `layer.tar` появляется только
если запрошен Docker archive. Грубая оценка того, сколько временного места
может понадобиться:

```text
registry / OCI archive:
    сумма размеров сжатых COPY-слоёв

Docker archive:
    сумма размеров сжатых COPY-слоёв + сумма размеров несжатых COPY-слоёв
```

Если среди целей публикации есть архив, слои базового образа тоже
дозагружаются на диск (см. следующую главу) — это добавляется к общему
объёму. Для Docker archive базовые слои по одному распаковываются во временное
несжатое представление. Сам временный файл итогового архива создаётся рядом с
целевым путём и не входит в расход `TMPDIR`. Поэтому в CI следует отдельно
учитывать свободное место в `TMPDIR` и на файловой системе назначения.

`TMPDIR` — переменная окружения, которую использует крейт `tempfile`. С её
помощью можно изменить каталог для временного хранения слоёв.
