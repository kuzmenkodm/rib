# Конфигурация образа, manifest и `scratch`

Этап assemble ("сборка") — это место, где базовый образ, новые
`--copy`-слои и метаданные запуска (entrypoint, labels, порты и т.д.)
сводятся в один неизменяемый `ImageBundle`. Это чисто CPU-шаг: он не ходит в
сеть и не трогает файловую систему, а работает только с типами данных
`oci-spec` (см. главу "Архитектура", раздел про `oci-client`/`oci-spec`).

## Как представлен базовый образ

Базовый образ описывается типом `Image`:

```text
Image {
    source: Option<ImageSource>,
    config: ImageConfiguration,
    layers: Vec<Descriptor>,
}
```

Поле `source` различает два принципиально разных случая:

- `Some(ImageSource)` — образ реально был скачан из registry; в нём
  сохранены исходная ссылка на образ и digest его manifest;
- `None` — это специальная пустая основа `scratch` (см. ниже).

Это разделение сделано намеренно: для `scratch` не нужно (и не должно быть)
никакой поддельной ссылки на registry или поддельного digest — ведь никакого
реального registry-образа тут нет, и такие фиктивные значения могли бы
случайно попасть в annotations готового образа или в логику публикации, введя
кого-то в заблуждение.

## Если образ взят из registry

Для обычной ссылки на образ (`--from alpine:3.22` и подобные) registry-адаптер
делает следующее:

1. определяет нужные credentials для этого registry;
2. скачивает manifest — либо, если это multi-platform index, сначала
   выбирает из него manifest под нужную вам платформу;
3. скачивает config (это небольшой JSON, не сами файлы образа);
4. считает SHA-256 от полученных байт config и сверяет его с тем digest,
   что заявлен в manifest — это защита от повреждённых или неожиданно
   изменённых данных;
5. проверяет, что `os`, `architecture` и (если вы его указали) `variant`
   в config совпадают с тем, что вы просили в `--platform`;
6. переводит descriptor'ы слоёв из внутреннего формата библиотеки
   `oci-client` в формат `oci-spec`, которым дальше пользуется весь
   остальной код;
7. сохраняет только descriptor'ы — сами байты слоёв (которые могут весить
   гигабайты) на этом шаге ещё не скачиваются.

Перед тем как перейти к сборке итогового образа, `rib` дополнительно
проверяет, что количество слоёв базового образа совпадает с количеством
записей `rootfs.diff_ids` в его config. Если это не так — значит, сам
базовый образ повреждён или собран с нарушением спецификации.

## `FROM scratch`

Точное слово:

```text
scratch
```

— это не имя реального образа, а специальное значение, означающее "начать с
абсолютно пустой файловой системы, без единого файла". Когда вы его
указываете, `rib`:

- не пытается разобрать его как ссылку на registry-образ;
- не создаёт клиент для обращения к какому-либо registry;
- не скачивает ни manifest, ни config, ни какие-либо байты;
- строит `ImageConfiguration` (config будущего образа) с нуля средствами
  `oci-spec`;
- берёт `os`, `architecture` и, если он указан, `variant` из вашего
  `--platform`;
- начинает с пустых `rootfs.diff_ids`, пустой `history` и пустого списка
  слоёв;
- не добавляет annotations с именем или digest базового образа, поскольку
  `scratch` не имеет registry-источника.

Важно не перепутать: специальное значение — это только точное слово
`scratch`. Значения вида `scratch:latest` или полный адрес наподобие
`registry.example.com/team/scratch:latest` — это обычные ссылки на
registry-образ (пусть даже кто-то и назвал свой образ так неудачно), и они
проходят стандартный путь скачивания, описанный в разделе выше.

После того как пустая основа создана, локальные `--copy`-слои строятся и
добавляются к ней точно так же, как и к любому другому базовому образу.
Разница проявляется только на выходе: OCI и Docker archive будут содержать
только ваши локальные слои (скачивать больше нечего), а публикация в
registry сразу загружает только собранные вами blobs.

Образ вообще без единого слоя — валиден с точки зрения спецификации OCI, но
в 99% случаев бесполезен: в него в принципе нечему исполняться. Чтобы
приложение реально заработало на основе `scratch` необходимо:

- собрать самодостаточный (обычно статически слинкованный) исполняемый файл —
  никакого динамического линкера внутри `scratch` нет, и обычный
  glibc-бинарник не сможет запуститься;
- явно задать `--entrypoint` — по умолчанию его тоже неоткуда унаследовать;
- скопировать набор корневых CA-сертификатов, если приложение устанавливает TLS-соединения
  (например, ходит в внешний API) — своего `/etc/ssl/certs` внутри `scratch`
  нет;
- любые другие рантайм-файлы, на которые приложение рассчитывает: конфиги,
  таймзоны, файл пользователей и т.д.

Для Rust-приложений типичный способ получить такой самодостаточный бинарник —
собрать его под musl-таргет (`x86_64-unknown-linux-musl` и подобные). Но
выбор toolchain и сама cross-компиляция — забота пользователя, а не `rib`
(см. также главу "Интеграция с Cargo").

## Как обновляется config

Assembler либо клонирует config базового образа, либо (для `scratch`)
получает пустой config с нуля, а затем:

1. проставляет `created` (время создания);
2. добавляет `diff_id` каждого нового слоя в конец `rootfs.diff_ids`;
3. если поле `history` существует, добавляет по одной непустой записи на
   каждый новый слой;
4. применяет ваши изменения метаданных запуска (см. правила ниже);
5. проверяет, что `history` и `rootfs` согласованы друг с другом;
6. сериализует итоговый config в JSON;
7. считает его digest.

Для записи `history`, которая относится к новому слою, `created_by`
выглядит так:

```text
rib copy (<uncompressed-size> bytes uncompressed)
```

Обратите внимание, чего там нет: ни исходных путей файлов, ни полной команды,
которой вы запустили `rib`. Это осознанное решение — такие детали могут
содержать чувствительную информацию (например, внутренние пути CI) и не
обязаны попадать в публикуемый образ.

## Как объединяются метаданные запуска

- Новый `--entrypoint`, если вы его задали, полностью заменяет `Entrypoint`
  базового образа.
- Когда entrypoint заменяется, `Cmd` базового образа очищается, если не указан
  `--keep-cmd` и не задан новый `--cmd`. Явный `--cmd` заменяет унаследованный
  `Cmd`.
- `--label` дополняет карту меток базового образа; если ключ уже существует,
  новое значение перезаписывает старое.
- `--port` добавляются к уже объявленным портам, без дублирования одного и
  того же порта дважды.
- `--workdir` и `--user` меняются, только если вы указали их явно — иначе
  остаются как в базовом образе.
- Всё остальное из метаданных базового образа (например `Env`) сохраняется
  без изменений.

Для `scratch` отсутствует источник наследуемых metadata. Runtime-поля config
содержат только явно переданные значения, но сам config также включает
платформу, `created`, `rootfs` и `history`, сформированные сборщиком.

## Инвариант между history и rootfs

Каждая непустая запись `history` должна соответствовать ровно одному
`diff_id` в `rootfs`. Записи с пометкой `empty_layer: true` — это
метаданные (например, `ENV` в оригинальном Dockerfile),
которые не добавляют новый слой файловой системы, и они в счёт не идут.

Перед тем как опубликовать что-либо, `rib` проверяет:

```text
количество(history, где empty_layer != true) == количество(rootfs.diff_ids)
```

Если это равенство не выполняется — значит, где-то в цепочке (обычно в
исходном базовом образе) есть рассогласование, и лучше остановиться с
понятной ошибкой, чем опубликовать образ с испорченными метаданными. Если у
базового config вообще нет `history` (такое бывает — это необязательное
поле), assembler сохраняет это как есть и не пытается её придумать. У
`scratch`, напротив, `history` изначально пустой список, поэтому новые
`--copy`-слои сразу получают свои записи.

## Как строится manifest

После того как config готов, assembler:

1. формирует descriptor для config;
2. переносит descriptor'ы слоёв базового образа в исходном порядке;
3. добавляет к ним descriptor'ы новых слоёв;
4. собирает из этого manifest;
5. добавляет annotation `org.opencontainers.image.created`;
6. если образ собран поверх реального registry-образа — добавляет ещё
   annotations с именем и digest этого базового образа;
7. сериализует manifest и считает его digest.

Manifest, собранный от `scratch`, не объявляет наследование от pullable image:
он содержит annotation о времени создания, но не содержит annotations с
именем и digest базового образа.

Исходный источник байт каждого слоя хранится в типе `LayerSource`:

```text
LayerSource::Built(Layer)              // слой, который построил сам rib

LayerSource::FromBase {                // слой, унаследованный от базового образа
    descriptor,
    source: ImageSource,
}
```

Это разделение позволяет коду, который пишет результат (registry, OCI
archive, Docker archive), самому решать, как получить байты каждого
конкретного слоя — взять локальный файл, лениво скачать его из registry или
вообще обойтись без скачивания через cross-repository mount (см. следующую
главу) — и при этом не менять сам manifest.
