# Registry и форматы архивов

После того как этап assemble отработал (см. предыдущую главу), каждая цель
публикации получает один и тот же готовый `ImageBundle`. Ни один из
writer'ов не пересобирает config или manifest заново — он лишь по-разному
записывает уже готовые данные. Отсюда полезное следствие: за один запуск
`rib build --to registry:... --to oci-archive:... --to docker-archive:...`
все три результата имеют один manifest digest и представляют один образ в
разных форматах доставки.

## Работа без предварительного pull базового образа

В начале сборки запрашиваются только manifest, config и descriptor'ы. Полный
base image не загружается на локальный диск. Байты его слоёв скачиваются
только в двух случаях:

- вы попросили archive (OCI или Docker) — а в архиве должны физически лежать
  вообще все слои образа, ведь archive должен быть самодостаточным файлом,
  не зависящим от доступности registry;
- выполняется публикация в registry, где blob отсутствует и не может быть
  переиспользован через mount из исходного репозитория (см. раздел про
  registry push ниже).

При наличии archive-цели `rib`
скачивает уникальные base-blobs параллельно (с ограничением `--jobs`) — ещё
до того, как начнётся сама запись архива. Локально построенные слои уже и
так лежат на диске, их скачивать не нужно.

При повторной публикации в registry существующие blob'ы определяются по
digest и не передаются повторно. Если source и target находятся в одном
registry, `rib` сначала пытается выполнить cross-repository mount. Таким
образом, registry выполняет роль content-addressed кэша без локального
`docker pull`.

Для `scratch` этот этап отсутствует, поскольку образ не содержит базовых
слоёв.

## OCI archive

OCI archive — это обычный tar-файл, внутри которого лежит структура,
определённая спецификацией OCI Image Layout:

```text
oci-layout
index.json
blobs/sha256/<manifest-hex>
blobs/sha256/<config-hex>
blobs/sha256/<layer-hex>
...
```

`index.json` содержит один descriptor итогового manifest для выбранной
платформы (см. главу "Модель OCI-образа", раздел про image index). Если в
цели публикации указан tag
(`--to oci-archive:image.tar@app:v1`), он записывается в этот descriptor как
annotation `org.opencontainers.image.ref.name` — именно так инструменты
например `skopeo` и `podman load`, получают тег из архива.

Config, manifest и слои лежат каждый по своему content-addressed пути
(путь равен digest объекта — см. главу "Введение"). Слои остаются сжатыми —
это тот же формат, что хранится в registry. Если один и тот же digest
встречается несколько раз (например, слой базового образа совпадает с одним
из ваших `--copy`), в архив он записывается только один раз — записывать
одинаковые байты дважды не имеет смысла.

Пример:

```bash
rib build ... \
  --to oci-archive:dist/image.tar@example/app:v1
```

## Docker archive

Docker archive — это формат, совместимый с классическим `docker save` /
`docker load`:

```text
manifest.json
<config-hex>.json
<diff-id-hex>/layer.tar
...
```

`manifest.json` содержит опциональный `RepoTags` и упорядоченный список
путей к слоям. В отличие от OCI archive, слои здесь лежат **несжатыми** —
так исторически устроен формат Docker save. Из-за этого Docker archive
обычно заметно больше по размеру, чем OCI archive того же образа.

Раз слои нужны несжатыми, `rib` во время сборки сохраняет для каждого нового
слоя ещё и несжатый `layer.tar` — но только если такой output вообще
запрошен (см. предыдущую главу про построение слоёв: без Docker archive этот
файл не создаётся, чтобы не тратить лишнее место на диске). Слои базового
образа, которые в registry хранятся сжатыми (gzip или zstd), при записи
такого архива распаковываются во временные файлы на лету.

Пример:

```bash
rib build ... \
  --to docker-archive:dist/image.tar@example/app:v1
```

## Как архив записывается атомарно

Ни один archive не появляется на итоговом месте сразу — сначала он целиком
пишется во временный файл рядом с целевым путём:

1. в него записываются все элементы tar;
2. writer сбрасывает буферы (`flush`);
3. для файла запрашивается синхронизация с диском (`fsync`);
4. временный файл атомарно переименовывается в целевой путь (одна операция
   файловой системы, без промежуточного состояния частично записанного файла).

Если запись архива завершается ошибкой до переименования, ранее существовавший
целевой файл остаётся неизменным. Временный файл создаётся рядом с целевым,
поскольку атомарное переименование гарантируется только в пределах одной
файловой системы.

## Публикация в registry

Для каждого уникального слоя `rib` выбирает способ доставки в целевой registry
в следующем порядке:

```text
blob уже есть в целевом репозитории?
    ├── да ─► переиспользовать без загрузки
    └── нет
        ├── это слой из того же registry, откуда взят base ─► попробовать cross-repository mount
        │                                                       ├── получилось
        │                                                       └── не получилось ─┐
        └── это собственный слой rib или другой registry ────────────────────────┴─► загрузить целиком
```

**Cross-repository mount** — операция registry API, которая добавляет в целевой
репозиторий ссылку на blob из другого репозитория того же registry без повторной
передачи данных. Это особенно полезно, когда base image и целевой образ лежат в
одном registry (например, оба в одном корпоративном Harbor или ghcr.io): все
унаследованные слои обычно подключаются без передачи данных, поэтому по сети
отправляются только новые `--copy`-слои.

Собственный (built) слой открывается прямо из локального временного
хранилища. Слой базового образа, если он всё же нужен, при необходимости
скачивается из исходного репозитория во временный файл и оттуда потоково
передаётся в целевой registry.

Загрузка слоёв идёт параллельно, с тем же ограничением `--jobs`. После всех
слоёв отдельным blob'ом отправляется config (если такого blob в registry ещё
нет). Manifest публикуется самым последним:

```text
слои ──► config ──► manifest
                       │
                       └── именно сейчас тег переключается на новый manifest
```

Публикация manifest — это точка "коммита". Если тег уже существовал, до этого
момента он продолжает указывать на прежний manifest. Загруженные blobs могут
переиспользоваться другими образами, но новый образ не становится доступен по
целевому тегу до публикации его manifest. Поэтому ошибка на более раннем шаге
не оставляет тег указывающим на частично загруженный образ.

## Потоковая передача и повторные попытки

Загрузка идёт блоками по 4 МиБ, файл читается потоково, а не грузится в
память целиком. Если во время передачи произошла временная ошибка, повторная
попытка открывает файл заново и читает с самого начала — докачки с прерванного
места пока нет.

Временные сетевые ошибки — таймауты, разрывы соединения, HTTP-коды `408`,
`425`, `429`, `500` и `502`–`599`, а также соответствующие ошибки уровня I/O —
повторяются автоматически, до трёх попыток, с экспоненциально растущей
паузой между ними и небольшим случайным сдвигом (jitter), чтобы несколько
параллельных сборок не били по восстанавливающемуся registry синхронными
залпами запросов. Ошибки аутентификации и несовпадения digest не
повторяются никогда — это осмысленный сигнал "повторять бессмысленно, тут
проблема не в сети", а не временный сбой.

Config и manifest — маленькие JSON, они целиком живут в памяти как байтовые
буферы. А вот сами слои никогда не загружаются в память целиком — они всегда
идут через файлы и потоки, поэтому память процесса не растёт вместе с
размером образа.

## Аутентификация и транспорт

Порядок разрешения учётных данных для конкретного registry:

1. явный флаг `--credential <registry>=<user>:<password>` (можно повторять);
2. секция `auths` из одного выбранного Docker config;
3. если credential не найден — анонимный доступ.

Docker config выбирается один раз: явно указанный через `--docker-config`
файл, иначе `$DOCKER_CONFIG/config.json`, иначе `~/.docker/config.json`. После
выбора файла fallback к другим Docker config не выполняется.

Алиасы Docker Hub (`docker.io`, `index.docker.io` и т.п.) приводятся к
каноническому имени `registry-1.docker.io`, чтобы credentials, сохранённые
под одним из этих имён, находились независимо от того, как вы обратились к
Docker Hub в `--from`/`--to`. Внешние credential helper'ы (`credsStore`,
`credHelpers` из Docker config) пока не запускаются — читается только сама
секция `auths`.

Источник (`--from`) и цель (`--to registry:...`) используют два разных
клиента registry. Из этого следует важная граница: `--from-plain-http` и
`--from-skip-tls` не ослабляют соединение с целевым registry, а
`--to-plain-http`/`--to-skip-tls`, наоборот, не трогают транспорт к
исходному registry. Но внутри одной из этих двух ролей граница уже не такая
тонкая — например, если у вас несколько `--to registry:...` в одной команде,
`--to-skip-tls` отключает проверку сертификата сразу для всех них
(подробнее и почему — в главе "Воспроизводимость и безопасность").

Обе эти опции (plain HTTP, отключённая проверка TLS-сертификата)
предназначены только для контролируемых локальных или dev-сетей — например,
локального test-registry в CI. Использовать их для реального production
registry не следует.
