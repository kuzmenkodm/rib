# Воспроизводимость и безопасность

Rootless-исполнение (см. главу "Назначение и принципы проекта") уменьшает
привилегии, которые нужны build-процессу — но само по себе оно *не* делает
входные данные автоматически воспроизводимыми или доверенными. Оба этих
свойства — не что-то, что появляется "само собой" от факта использования
`rib`: их обеспечивает явная политика вашего pipeline.

## Что значит "воспроизводимый результат"

Цель reproducible-режима простая: одни и те же входные данные при одной и
той же версии `rib` и его зависимостей должны давать байт-в-байт одинаковые
слои, config и manifest. Это не "тот же смысл", а именно тот же набор байт
— вплоть до совпадающего digest.

Обычный tar/gzip так себя не ведёт "из коробки" — в него незаметно
просачивается множество источников случайности: время модификации файла,
порядок обхода каталога, права по умолчанию, конкретный алгоритм сжатия.
`rib` явно убирает всё это:

- записи внутри tar всегда идут в отсортированном порядке;
- `mtime` (время модификации) у каждой записи всегда равно `0`;
- uid/gid по умолчанию — `0`, если явно не указан `chown`;
- имя пользователя/группы в заголовке всегда пустое;
- права нормализуются по фиксированным правилам (см. главу "Построение
  COPY-слоёв");
- сжатие gzip всегда использует один и тот же уровень —
  `Compression::fast()`;
- время создания образа (`created`) по умолчанию равно
  `1970-01-01T00:00:00Z` (Unix-эпоха), а не текущему моменту;
- результаты параллельно построенных `--copy`-слоёв всегда возвращаются в
  исходный порядок, независимо от того, какой из них реально досчитался
  первым.

Единственное исключение, которое сделано намеренно: `--creation-time now`
специально делает config и manifest зависимыми от момента запуска (а значит
— невоспроизводимыми между двумя запусками в разное время). Если вам важна
воспроизводимость, используйте либо значение по умолчанию (`epoch`), либо
один и тот же фиксированный RFC3339-timestamp, переданный явно — например,
время коммита, а не время сборки.

## Факторы, влияющие на результат

На итоговые байты влияет больше вещей, чем может показаться на первый
взгляд:

- содержимое и бит "исполняемый" у исходных файлов;
- список и порядок ваших `--copy`;
- явно заданные `mode` и `chown`;
- выбранная платформа (`--platform`);
- config и descriptor'ы слоёв базового образа;
- флаги метаданных образа (`--label`, `--port`, `--entrypoint` и т.д.);
- версия самого `rib`, а также версии библиотек сжатия и сериализации,
  которые он использует.

Тег базового образа (`alpine:3.22` и подобные) — изменяемая ссылка: тот, кто
управляет registry, может в любой момент подвинуть его на другой manifest.
Если вам нужен строго повторяемый результат, зафиксируйте базовый образ по
digest, а не по тегу:

```bash
rib build \
  --from alpine@sha256:<manifest-digest> \
  --platform linux/amd64 \
  ...
```

Отдельно стоит понимать: даже при абсолютно одинаковых входных данных
обновление самого `rib` (например, если поменяется реализация сжатия в одной
из зависимостей) может изменить байты результата, даже если *смысл* образа
остался прежним. Поэтому версию `rib`, которой собран образ, стоит считать
частью его provenance (происхождения) — и фиксировать её в CI, а не
полагаться на "последнюю версию".

## Целостность данных

При скачивании базового образа digest его config пересчитывается заново и
сверяется с тем, что заявлен в manifest — это ловит как повреждение при
передаче, так и вредоносную подмену контента, если бы кто-то попытался её
устроить (см. главу "Конфигурация образа, manifest и scratch"). Descriptor'ы слоёв служат
идентификаторами содержимого для самого registry. На этапе assemble
дополнительно проверяются внутренние согласованности: совпадает ли число
слоёв с числом `diff_ids`, согласована ли `history` с ними и т.д.

Итоговая сводка, включая config digest, выводится в stderr. Если stdout не
является терминалом, в него после успешной сборки выводится только manifest
digest. CI может сохранить его как неизменяемую ссылку на результат:

```text
registry.example.com/team/server@sha256:...
```

Такая ссылка по digest, в отличие от ссылки по тегу, физически не может
начать указывать на что-то другое — в этом смысле она надёжнее для
production деплоя.

`rib` не подписывает digest и не генерирует provenance-аттестации. Выделенный
stdout позволяет передать digest следующему этапу без разбора лога:

```bash
IMAGE_DIGEST="$(rib build ... --to registry:registry.example.com/team/app:v1)"
cosign sign "registry.example.com/team/app@${IMAGE_DIGEST}"
```

## Credentials

Несколько практических правил при работе с учётными данными registry:

- предпочитайте read-only Docker config или внешний secret store прямой
  передаче пароля;
- не храните credentials в `Cargo.toml` — эта секция специально
  спроектирована так, чтобы их туда положить было нельзя (см. главу "Cargo
  integration");
- не включайте `set -x` в shell-скрипте, если в той же команде используется
  `--credential` — иначе пароль попадёт прямо в лог команд;
- ограничивайте токен конкретным репозиторием и минимально необходимыми
  правами (pull и/или push), а не выдавайте токен с широким доступом ко
  всему registry;
- если этого требует ваша модель угроз, разделяйте учётные записи для
  чтения source-образа и для публикации в target — тогда компрометация
  одной не даёт немедленного доступа к другой. `rib` выбирает credential по
  имени registry, поэтому разные учётные записи можно задать только для разных
  registry-хостов; для двух репозиториев одного registry разделение ролей
  внутри одного запуска не поддерживается.

## TLS

По умолчанию HTTPS и проверка сертификата включены всегда — их нужно
осознанно отключать самостоятельно. Есть два разных флага, которые ослабляют
защиту по-разному: plain HTTP отключает шифрование вообще (трафик к registry
идёт открытым текстом), а `--*-skip-tls` оставляет HTTPS, но принимает
недоверенный или самоподписанный сертификат, то есть не подтверждает
идентичность удалённого registry.

Транспорт для источника и для целей публикации настраивается раздельно
(`--from-*` и `--to-*` — см. главу "Registry и форматы архивов"), но
внутри одной из этих двух ролей защита ослабляется целиком, а не для одного
конкретного адреса. Например, если в одной команде указано несколько `--to
registry:...` на разные хосты, `--to-skip-tls` отключит проверку
сертификата у них у всех сразу — потому что все они физически используют
один и тот же HTTP-клиент. **Не объединяйте в одной команде dev-цель, для
которой вы включили `--to-skip-tls`, и настоящую production-цель** — иначе
production-соединение окажется без защиты, хотя вы хотели ослабить её только
для тестового registry.

## `--copy` как граница доверия

`rib` может прочитать любой файл, который вы явно указали в `--copy`, или
который попал под glob-шаблон. Если по невнимательности передать целый
каталог (например, корень репозитория), в образ может случайно попасть:

- файл `.env` с секретами;
- приватные ключи;
- credentials для Cargo (`~/.cargo/credentials.toml` и подобные, если они
  случайно оказались внутри копируемого дерева);
- исходный код и метаданные системы контроля версий (`.git`);
- логи сборки.

В `rib` нет аналога `.dockerignore` — единственная граница того, что попадёт
в образ, это то, что вы явно перечислили в `--copy`. Используйте узкие,
точечные пути вместо широких каталогов и проверяйте итоговый архив или образ в
CI. Для анализа файловой системы можно использовать `dive`; OCI archive также
можно распаковать специализированным OCI-инструментом или проверить, распаковав
нужные layer blobs. Обычный `tar -tf` показывает только внешнюю структуру OCI
archive, а `docker history` не перечисляет файлы образа.

Символические ссылки как источник `--copy` отклоняются с ошибкой — поэтому
через симлинк нельзя незаметно "выбраться" за пределы ожидаемого дерева
файлов. Так же отклоняется destination-путь, содержащий `.`/`..` или пустые
компоненты пути — эти два правила вместе не дают образу случайно получить
файл там, где вы этого не ожидали.

## `scratch` и безопасность рантайма

`scratch` уменьшает количество файлов и пакетов внутри образа, поскольку
содержит только явно добавленные данные. Однако выбор `scratch` сам по себе не
обеспечивает безопасность приложения. Необходимо учитывать:

- статические зависимости внутри бинарника и их своевременное обновление
  (если в статически слинкованной библиотеке найдут уязвимость, `apt
  upgrade` внутри образа её не исправит — нужно пересобрать сам бинарник);
- набор CA-сертификатов, если приложение делает исходящие TLS-запросы;
- корректный непривилегированный `--user` вместо root;
- отсутствие секретов внутри скопированных конфигов;
- наблюдаемость приложения без shell и средств отладки внутри образа;
- сканирование самого исполняемого файла на уязвимости.

Минимальный образ сложнее исследовать "изнутри" после того, как он уже
запущен — в нём в принципе нет shell, чтобы туда зайти. Поэтому диагностику
стоит закладывать на уровне самого приложения (логи, метрики, health-checks),
а для разовой отладки в Kubernetes — рассчитывать на ephemeral debug
containers, которые подключаются к поду отдельно, а не полагаться на то, что
внутрь можно будет зайти обычным `kubectl exec`.

## Безопасность публикации

Archive заменяет собой файл по целевому пути только после того, как он
полностью записан и синхронизирован с диском (см. главу "Registry и
форматы archive", раздел про атомарную запись). Manifest в registry
отправляется только после того, как загружены все слои и config. Обе эти
меры защищают от ситуации "снаружи виден наполовину записанный результат" —
но, как уже говорилось в главе "Эксплуатация", несколько целей публикации за
один запуск (`--to A --to B`) всё равно не образуют одну общую транзакцию:
успех или неуспех одной цели не откатывает другую.
