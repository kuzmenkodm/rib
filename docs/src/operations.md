# Эксплуатация

`rib` рассчитан прежде всего на неинтерактивный запуск в CI/CD, но использует
тот же интерфейс и при локальной работе. В production-конвейере рекомендуется
явно фиксировать платформу, версию сборщика, базовый образ и параметры
сетевого транспорта.

## Прогресс, stderr и stdout

Флаг `--progress` принимает четыре значения:

| Режим | Назначение |
|---|---|
| `auto` | Интерактивный интерфейс при терминальном stderr, иначе построчный вывод |
| `color` | Принудительный интерактивный интерфейс |
| `plain` | Стабильные построчные сообщения для CI-логов |
| `quiet` | Отключение сообщений о ходе операций; итоговая сводка сохраняется |

Прогресс, предупреждения и итоговая сводка направляются в stderr. Когда stdout
не является терминалом, успешная сборка выводит в него только manifest digest
без префикса и завершающего перевода строки:

```text
sha256:0123456789abcdef...
```

Благодаря разделению потоков digest можно безопасно получить через command
substitution, не разбирая человекочитаемый лог:

```bash
IMAGE_DIGEST="$(rib build \
  --progress plain \
  --from scratch \
  --platform linux/amd64 \
  --copy ./server:/server,mode=0755 \
  --entrypoint /server \
  --to registry:registry.example.com/team/server:v1)"

cosign sign "registry.example.com/team/server@${IMAGE_DIGEST}"
```

Не включайте shell tracing (`set -x`) в блоке, где в командной строке
передаются credentials: оболочка может записать исходные аргументы в лог до
запуска `rib`.

## Параллельность

`--jobs` устанавливает общий предел параллельных операций для:

- построения `COPY`-слоёв;
- скачивания blob'ов базового образа;
- загрузки blob'ов в целевой registry.

Значение по умолчанию равно числу доступных CPU, но не превышает четырёх.
Увеличение `--jobs` может ускорить сетевые операции, одновременно повышая
нагрузку на CPU, диск и registry. В среде с ограниченным ephemeral storage
или пропускной способностью значение следует уменьшить.

Цели `--to` обрабатываются последовательно в порядке объявления. Операции со
слоями внутри одной registry-цели выполняются параллельно.

## Временные данные и кэш базовых слоёв

Временные файлы слоёв создаются в системном временном каталоге (`TMPDIR` на
Unix). Для registry и OCI archive локальный `COPY`-слой обычно хранится только
в сжатом виде. Если запрошен Docker archive, дополнительно сохраняется его
несжатое представление. Временный файл самого итогового архива создаётся рядом
с целевым путём, а не в `TMPDIR`.

Для больших образов рекомендуется выделять отдельный volume под `TMPDIR` и
задавать лимит ephemeral storage с учётом:

- сжатых локальных слоёв;
- скачанных слоёв базового образа;
- несжатых слоёв Docker archive;
- временного файла локального архива на файловой системе его назначения.

Цели публикации обрабатываются последовательно, поэтому несколько локальных
архивов не записываются одновременно.

По умолчанию скачанные base-blobs не сохраняются между запусками. Постоянный
кэш включается явно:

```bash
rib build ... --cache
rib build ... --cache --cache-path /cache/rib
```

Без `--cache-path` используется каталог `./.rib-cache`. При чтении кэшированный
blob повторно хэшируется; повреждённое содержимое не используется. Кэш хранит
скачанные слои базового образа, но не кэширует построенные `COPY`-слои и не
заменяет кэш Cargo, npm или другого инструмента сборки приложения.

Один каталог кэша не следует одновременно использовать для записи несколькими
процессами `rib`. Для параллельных CI-задач применяйте отдельные каталоги либо
сериализуйте запись на уровне CI.

Прямой push в тот же registry обычно не требует локального кэша: существующие
blob'ы переиспользуются средствами registry без предварительного скачивания.

## Сетевой транспорт

Значения по умолчанию:

- таймаут соединения — 30 секунд;
- таймаут чтения — 60 секунд;
- максимальное число попыток — 3;
- HTTPS с обязательной проверкой сертификата.

Параметры `--connect-timeout`, `--read-timeout` и `--max-attempts` позволяют
изменить эти значения. Plain HTTP и отключение проверки TLS настраиваются
раздельно для source- и target-registry:

- `--from-plain-http`, `--from-skip-tls`;
- `--to-plain-http`, `--to-skip-tls`.

Флаги `*-skip-tls` ослабляют проверку для всех registry соответствующей роли в
рамках запуска. Их допустимо использовать только для доверенной тестовой
инфраструктуры.

## Несколько целей публикации

Один запуск может создать несколько представлений одного образа:

```bash
rib build \
  --from alpine:3.22 \
  --platform linux/amd64 \
  --copy ./server:/app/server,mode=0755 \
  --entrypoint /app/server \
  --to registry:registry.example.com/team/server:v1 \
  --to oci-archive:dist/server-oci.tar@server:v1 \
  --to docker-archive:dist/server-docker.tar@server:v1
```

Config и manifest формируются один раз, поэтому все цели имеют один manifest
digest. Публикация нескольких целей не является общей транзакцией: ошибка
поздней цели не откатывает уже записанные архивы и registry manifest'ы.

## Логи и диагностика

Для подробной диагностики используется переменная `RIB_LOG`:

```bash
RIB_LOG=rib=debug rib build --progress plain ...
```

`RUST_LOG` намеренно не используется, поскольку `cargo rib build` запускает
сборку пользовательского Rust-проекта, который может интерпретировать эту
переменную самостоятельно.

Режим `color` предназначен для терминала и может добавлять управляющие
последовательности. Для CI следует использовать `plain`, `quiet` или `auto`.

## Завершение и частично опубликованные данные

Ctrl-C прерывает верхнеуровневую операцию. COPY-воркеры используют
кооперативную отмену и завершаются при очередной проверке сигнала во время
записи; отдельного обработчика SIGTERM в текущей версии нет.

Локальный archive сначала полностью записывается во временный файл рядом с
целевым путём и только затем публикуется атомарным rename. Manifest registry
отправляется после слоёв и config, поэтому тег не начинает ссылаться на
частично загруженный образ. Уже загруженные, но не связанные manifest'ом
blob'ы могут оставаться в registry до его штатной garbage collection.
