# Архитектура

Глава описывает внутренние компоненты и общий конвейер сборки. Детали
формирования слоёв, OCI config, manifest и output-форматов приведены в
следующих разделах.

Система предоставляет два интерфейса: standalone CLI `rib build` и Cargo
integration `cargo rib build`. Оба используют один конвейер:

```text
rib build   ─────────────┐
                         ├──► ImageBuildSpec ──► BuildRequest
cargo rib build ─► cargo ┘                         │
                                                   ▼
                         ┌────────────────────────────────────┐
                         │ base image + parallel COPY build   │
                         └─────────────────┬──────────────────┘
                                           ▼
                                      ImageBundle
                                           │
                         ┌─────────────────┼─────────────────┐
                         ▼                 ▼                 ▼
                    OCI archive      Docker archive       registry
```

После формирования `ImageBuildSpec` источник запроса не влияет на дальнейшую
обработку.

## Ответственность модулей

| Модуль | Что делает |
|---|---|
| `cli` | Разбирает флаги standalone CLI в спецификацию сборки |
| `cargo_integration` | Запускает `cargo metadata`, выбирает нужный package в workspace, объединяет `Cargo.toml` и CLI-флаги, запускает `cargo build` |
| `app::build` | Проверяет корректность запроса и управляет сборкой целиком |
| `builder::copy` | Разбирает выражение `--copy`, раскрывает glob-шаблоны и вычисляет, куда внутри image должен попасть каждый файл |
| `builder::layer` | Строит детерминированный tar/gzip для одного слоя и считает его идентификаторы |
| `image` | Хранит platform, base image и источник слоя |
| `image::assemble` | Собирает финальные config и manifest в единый `ImageBundle` |
| `registry` | Обёртка над библиотекой `oci-client`: скачивание, операции с blobs, публикация manifest, повторные попытки при сетевых сбоях |
| `app::push` | Выбирает способ доставки слоя: переиспользование, cross-repository mount или загрузка |
| `blob` | Лениво скачивает base-слои и при необходимости распаковывает их (для Docker archive) |
| `cache` | Индексирует и проверяет постоянный кэш скачанных base-blobs |
| `archive` | Создает OCI/Docker архивы образа |
| `auth` | Читает Docker config, явные credentials из флагов и приводит имя registry к канонической форме |
| `progress` | Индикаторы прогресса: интерактивные в терминале, построчные в CI-логах, тихий режим |

`rib` и `cargo-rib` делегируют выполнение библиотечным функциям
`rib::run()` и `rib::run_cargo()`. Общая реализация исключает расхождение
жизненного цикла и обработки между интерфейсами.

## Нормализация запроса

Флаги standalone CLI сначала превращаются в `BuildArgs`, потом — в
`ImageBuildSpec`. Cargo-плагин строит тот же `ImageBuildSpec`, но
предварительно объединяет значения из `[package.metadata.rib]` и
командной строки (правила объединения описаны в главе про Cargo
integration). Далее оба пути проходят через `BuildRequest::try_from`, который
проверяет основные инварианты до начала сетевых и файловых операций:

- `--jobs` больше нуля;
- указана хотя бы одна цель публикации (`--to`);
- `--platform` имеет форму `<os>/<arch>[/<variant>]`, например
  `linux/amd64` или `linux/arm64/v8`;
- каждый `--label` — это пара `key=value`;
- у портов без явного протокола (`--port 8080`) подставляется `/tcp`;
- `--creation-time` — это либо `epoch`, либо `now`, либо валидный RFC3339;
- слово `scratch` распознаётся как специальная пустая основа; всё остальное
  парсится как обычная ссылка на registry image (`oci_client::Reference`).

После проверки остальные компоненты работают с единым типом запроса и не
зависят от использованного интерфейса запуска.

## Две независимые ветки в начале сборки

Скачивание манифеста базового образа и сборка локальных `--copy`-слоёв не
зависят друг от друга и выполняются параллельно. Для `scratch` сетевая ветка
отсутствует:

```text
registry base                            scratch
─────────────                            ───────
скачать manifest + config ─┐             создать пустой config  ─┐
                           ├─► assemble                          ├─► assemble
собрать COPY-слои  ────────┘             собрать COPY-слои ──────┘
```

На этом шаге скачиваются только manifest и config базового образа, но не байты
его слоёв, размер которых может составлять гигабайты. Base-слои загружаются
позднее только при необходимости: для включения всех данных в самодостаточный
archive либо если целевой registry не смог переиспользовать слой другим
способом.

## Граница асинхронных и блокирующих операций

Работа с registry является сетевым I/O и выполняется через async API
`oci-client`. Создание tar-архива, gzip-сжатие и обход файловой системы
относятся к CPU- и disk-bound операциям и не должны блокировать потоки Tokio.
Поэтому каждый `--copy` выполняется через `tokio::task::spawn_blocking` в
отдельном пуле потоков.

Число одновременно работающих `--copy`-воркеров ограничивает семафор размера
`--jobs`. На последующих этапах отдельные семафоры с тем же числовым пределом
ограничивают скачивание и загрузку blobs. Эти этапы не используют один общий
экземпляр семафора. Ограничение предотвращает неограниченный рост нагрузки на
CPU, диск и сеть.

Каждая `--copy`-задача возвращает пару "исходный индекс + готовый слой".
Координатор складывает результаты по индексу, а не в порядке завершения —
поэтому то, в каком порядке слои реально собрались, никак не влияет на их
порядок в итоговом manifest.

## Assemble — граница между "сырыми данными" и готовой моделью

До этапа assemble система работает с двумя исходными представлениями данных:

- descriptor'ы и config базового образа — либо скачанные из registry, либо
  сконструированные с нуля для `scratch`;
- локальные `Layer`'ы — с их digest, `diff_id` и путём к временным файлам на
  диске.

`image::assemble` сводит всё это в один `ImageBundle`:

```text
ImageBundle {
    config,                    // финальный config
    config_bytes,              // его байты, как они будут записаны/отправлены
    config_digest,
    manifest_bytes,            // финальный manifest
    manifest_digest,
    layers: Vec<LayerSource>,  // упорядоченный список слоёв, откуда их брать
}
```

Публикация в registry и оба archive writer получают один `ImageBundle` и один
упорядоченный список слоёв. Поэтому все цели одного запуска используют один
manifest digest.

## Жизненный цикл временных данных

Локальный слой хранит `Arc<LayerStorage>` — общую ссылку на временный
каталог, в котором обязательно лежит `layer.tar.gz`, а опционально ещё и
несжатый `layer.tar` (он нужен только для Docker archive). Благодаря `Arc`
клонирование `ImageBundle` не копирует данные: несколько writer'ов (например,
OCI archive и registry push) используют один файл на диске.

Скачанные base-слои индексируются по digest и переиспользуются между целями
одного запуска. Без `--cache` временные файлы удаляются после освобождения
последнего владельца. При `--cache` base-blobs сохраняются в `.rib-cache` либо
каталоге `--cache-path` и перед повторным использованием проверяются по
digest. Построенные `COPY`-слои между запусками не кэшируются.

## Обработка ошибок и отмены

На каждой границе — разбор параметров, `--copy`-воркер, скачивание, assemble,
запись архива, публикация в registry — ошибка сопровождается контекстом. 
Если один из `--copy`-воркеров падает с ошибкой, координатор:

1. взводит общий `CancellationToken` (сигнал отмены, общий для всех задач);
2. отменяет остальные ещё не завершённые async-обёртки;
3. дожидается завершения этих обёрток;
4. возвращает исходную ошибку — ту, что случилась первой, а не какую-то
   производную от отмены.

Блокирующую задачу `spawn_blocking` нельзя принудительно остановить. Специальный
`CancellableWriter` проверяет сигнал во время записи tar-потока, поэтому воркер
завершается кооперативно при очередной проверке и не обязан дочитывать большой
файл до конца.

На верхнем уровне обрабатывается Ctrl-C. Порядок публикации выбран так, чтобы
незавершённая команда не могла испортить уже готовый результат: archive
публикуется атомарно (см. главу про registry и archive), а manifest в
registry отправляется самым последним — так что прерванная на середине
команда не может оставить registry-тег указывающим на неполный image.

## Граница `oci-client` и `oci-spec`

`rib` опирается на две сторонние библиотеки с разными задачами:
`oci-client` умеет говорить по протоколу registry (аутентификация,
скачивание/загрузка blobs, работа с manifest), а `oci-spec` описывает сами
типы данных OCI — descriptors, digests, image config, manifest, index.

Registry-адаптер (модуль `registry`) — это единственное место, которое
переводит транспортные типы `oci-client` в типы `oci-spec`, и делает это
сразу после скачивания. Весь остальной pipeline после этой границы работает
только с одной моделью данных (`oci-spec`) и не создаёт дублирующие структуры.
Собственные типы `rib` используются только
там, где они описывают что-то, чего нет в стандартных библиотеках: сравнение
платформ, происхождение слоя (`LayerSource`), временное хранилище на диске,
опции сборки и цели публикации.
