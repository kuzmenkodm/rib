# Назначение и принципы проекта

`rib` предназначен для заключительного этапа сборочного конвейера: приложение
уже скомпилировано и протестировано, после чего готовый артефакт и необходимые
runtime-файлы требуется упаковать в образ и опубликовать в registry либо
сохранить в архиве.

```text
исходный код
    │
    ▼
компиляция и тестирование
    │
    ▼
готовый артефакт + runtime-файлы
    │
    ▼
rib
    ├──► registry
    ├──► OCI archive
    └──► Docker archive
```

Для проектов на Rust предусмотрена интеграция с Cargo — `cargo rib build`.
Команда сначала запускает `cargo build`, затем передаёт полученный артефакт в
общий конвейер формирования образа. Standalone-команда `rib build` сборку
приложения не выполняет.

## Rootless-сборка файловыми операциями

`rib` не запускает процессы внутри собираемого образа. Новые слои создаются
исключительно из файлов, указанных через `--copy` или
`[package.metadata.rib]`. Для этого требуются только:

- чтение исходных файлов;
- запись временных tar/gzip-файлов;
- сетевой доступ к OCI Registry API;
- разрешение на запись локального архива, если он запрошен.

Сборщику не требуются Docker daemon, container runtime, overlayfs, mount
namespace, доступ к сокету Docker или запуск контейнера.
Владелец и права файлов внутри будущего образа записываются непосредственно в
tar-заголовки, поэтому для `chown` внутри образа не нужны соответствующие права
на файловой системе хоста.

Такая модель уменьшает объём привилегий сборочного задания и делает запуск в
Docker и Kubernetes обычной непривилегированной операцией.

## Работа с базовым образом

Перед сборкой `rib` получает из registry только manifest, config и descriptor'ы
слоёв базового образа. Полный аналог `docker pull` не выполняется: байты
унаследованных слоёв не загружаются заранее на локальный диск без необходимости.

При публикации в registry применяется content-addressed модель OCI:

1. если blob уже существует в целевом репозитории, повторная передача не
   выполняется;
2. если исходный и целевой репозитории находятся в одном registry, выполняется
   попытка cross-repository mount;
3. только отсутствующий blob загружается из исходного registry и передаётся в
   целевой.

При повторных сборках registry остаётся источником истины и одновременно
хранилищем переиспользуемых слоёв. Все базовые слои скачиваются для создания
OCI/Docker archive. При публикации в registry скачиваются только те blobs,
которые целевой registry не смог переиспользовать.

## Кэширование сборочного окружения

Современные CI-задачи обычно выполняются внутри Docker-контейнеров или подов
Kubernetes. В этой модели `rib` можно добавить непосредственно в образ
сборочного окружения: например, в образ на базе Node.js Alpine вместе с
инструментами сборки фронтенда.

Container runtime на runner'е кэширует такой образ стандартным способом.
Повторное задание быстро запускается в уже подготовленном окружении, где
присутствуют Node.js, зависимости ОС и `rib`. Отдельный контейнер с daemonless-
сборщиком и отдельный перенос внутреннего кэша сборщика между заданиями не
требуются.

Кэш зависимостей приложения (`node_modules`, Cargo registry, `target` и т.п.)
при этом остаётся обычным кэшем CI. Дополнительный флаг `rib build --cache`
относится только к скачанным blob'ам базового образа. Построенные в процессе
сборки `COPY`-слои в этот кэш не попадают.

## Композиция с системами подписи

`rib` не реализует подпись образов самостоятельно. Вместо этого интерфейс
сборщика рассчитан на композицию с `cosign` и другими инструментами
supply-chain security.

Человекочитаемый прогресс и итоговая сводка выводятся в stderr. Если stdout
перенаправлен или используется в command substitution, в него выводится только
manifest digest вида `sha256:...`:

```bash
IMAGE_DIGEST="$(rib build ... --to registry:registry.example.com/team/app:v1)"
cosign sign "registry.example.com/team/app@${IMAGE_DIGEST}"
```

Скрипту не требуется разбирать текстовый лог. Digest является неизменяемым
идентификатором опубликованного manifest и может быть непосредственно передан
системе подписи, аттестации или развёртывания.

## Осознанные границы

`rib` не реализует работу с Dockerfile и не предназначен для выполнения
произвольных команд внутри образа. В частности, он:

- не поддерживает `RUN` и установку пакетов во время упаковки;
- не выполняет cross-compilation и эмуляцию другой архитектуры;
- не определяет автоматически артефакт Cargo или способ его линковки;
- не формирует multi-platform index за один запуск;
- не подписывает образ и не создаёт SBOM или provenance самостоятельно.

Если финальный образ требует изменения rootfs командами `RUN`, следует
использовать полноценный Dockerfile-совместимый builder. `rib` оптимален для
сценария, в котором все необходимые файлы уже подготовлены, а заключительный
этап должен быть rootless, воспроизводимым и удобным для автоматизации.
