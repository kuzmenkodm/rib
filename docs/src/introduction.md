# Модель OCI-образа

OCI-образ представляет собой набор content-addressed объектов, связанных
descriptor'ами. `rib` формирует эти объекты напрямую по правилам OCI Image
Specification, без запуска Docker daemon и без создания временного
контейнера.

В этой главе определены термины layer, digest, manifest и config, которые
используются далее в описании интерфейса и архитектуры.

## Аналогия: image как список патчей поверх файловой системы

Представьте пустую файловую систему. Каждый **layer** (слой) — это набор
изменений над ней: добавить файл, заменить файл, положить каталог. Если
наложить слои друг на друга по порядку, получится готовая файловая система
контейнера — это похоже на то, как серия git-коммитов, применённая по
порядку, даёт итоговое состояние репозитория.

`rib` не умеет делать все виды изменений, которые умеет Dockerfile (нет
`RUN`, нет удаления файлов через отдельный слой). Он умеет только один вид
слоя: "взять эти файлы с диска и положить их по таким путям внутри образа".
Такой слой создаётся командой `COPY` (`--copy`).

## Как идентифицируются объекты: descriptor и digest

У image нет единого "имени файла" для каждой его части. Вместо этого каждый
объект — слой, config, manifest — идентифицируется по **хешу собственного
содержимого** (SHA-256). Такой хеш называется **digest**, и он играет роль
отпечатка: если поменять хотя бы один байт объекта, его digest изменится.

Ссылка на объект (**descriptor**) — это маленький JSON, который говорит "вот
где искать этот объект и как проверить, что он не повреждён":

```json
{
  "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
  "digest": "sha256:def456...",
  "size": 28471122
}
```

Сам descriptor не содержит объект — только его тип, размер и digest. Реальные
байты хранятся отдельно (в registry — по HTTP, в OCI archive — в подкаталоге
`blobs/`), и все они лежат под именем, равным своему digest. Такое хранение
называется **content-addressable storage**: путь к файлу определяется его
содержимым. У этого подхода есть практическое следствие, важное для `rib`:
если две сборки производят байт-в-байт одинаковый слой, registry увидит один
и тот же digest и не станет загружать его второй раз.

## Layer: слой файловой системы

Layer — это обычный tar-архив, только договорённость такая: он описывает не
всю файловую систему, а лишь её изменение относительно предыдущего слоя.
Слои применяются по порядку, в котором перечислены в manifest — более поздний
слой может переопределить путь, добавленный более ранним.

Новый слой, который создаёт `rib` из `--copy`, — детерминированный
(при одинаковых входных файлах получается одинаковый tar, байт в байт) и
сжатый gzip. Внутри — только те файлы и каталоги, которые вы явно указали.
`rib` не выполняет никаких команд внутри контейнера и не пытается вычислить
diff файловой системы: он упаковывает только явно указанные данные.

Поскольку порядок слоёв — часть смысла image (слой №2 может переписать файл
из слоя №1), `rib` может строить несколько `--copy`-слоёв параллельно (это
быстрее), но перед тем как собрать итоговый image, обязательно возвращает их
в тот порядок, в котором вы перечислили `--copy` в командной строке —
независимо от того, какой из них фактически собрался первым.

## Config: как запускать контейнер

Config — это JSON, который описывает не файлы, а *метаданные запуска*:

- `architecture`, `os` и, опционально, `variant` — под какую платформу собран
  image (например `linux/amd64`);
- `config.Entrypoint`, `config.Cmd`, `config.Env` — что и с какими
  аргументами/окружением запускать;
- `config.WorkingDir`, `config.User` — рабочий каталог и от какого
  пользователя работает процесс;
- `config.ExposedPorts`, `config.Labels` — какие порты и метки объявлены;
- `rootfs.diff_ids` — список идентификаторов *содержимого* слоёв в порядке их
  применения (подробнее — ниже, в разделе про `diff_id`);
- `history` — история создания образа. Непустая запись соответствует слою, а
  запись с `empty_layer: true` описывает изменение metadata без нового слоя;
- `created` — время создания.

Если вы собираете image поверх существующего base image из registry, `rib`
берёт его config, обновляет в нём список слоёв, history и `created`, а затем
применяет ваши явные изменения (`--entrypoint`, `--label` и т.д.). Всё
остальное — например `Env` базового образа — остаётся как было. Интерфейса для
изменения `Env` в текущей версии нет.

Если вы начинаете с `FROM scratch` (пустой основы, без каких-либо файлов),
config собирается с нуля. Standalone CLI использует значение `--platform` или
его значение по умолчанию `linux/amd64`; в Cargo-интеграции платформа должна
быть задана через CLI или metadata. Списки слоёв и history изначально пустые.
`scratch` — это не какой-то
реальный образ из registry, а специальное точное слово, означающее "начать с
абсолютно пустой файловой системы".

## Manifest: оглавление одного image

Manifest — небольшой JSON, который связывает config и упорядоченный список
слоёв в одно целое:

```json
{
  "schemaVersion": 2,
  "mediaType": "application/vnd.oci.image.manifest.v1+json",
  "config": {
    "mediaType": "application/vnd.oci.image.config.v1+json",
    "digest": "sha256:abc123...",
    "size": 1842
  },
  "layers": [
    {
      "mediaType": "application/vnd.oci.image.layer.v1.tar+gzip",
      "digest": "sha256:def456...",
      "size": 28471122
    }
  ]
}
```

Manifest — это корень одного конкретного image под одну конкретную платформу.
Тег в registry является *изменяемой* ссылкой на digest manifest или
multi-platform image index. В случае platform-specific образа тег указывает
непосредственно на manifest digest. Сам manifest digest *неизменяем*: он
посчитан от содержимого файла и однозначно определяет байты config и слоёв, на
которые он ссылается. Поэтому
`registry.example.com/app@sha256:...` — куда более надёжная ссылка для
production, чем изменяемый тег: она гарантированно указывает на один и тот же
результат сборки.

## Image index: несколько платформ под одним тегом

Когда один тег должен работать одновременно на `linux/amd64` и
`linux/arm64`, registry использует **image index** — список descriptor'ов
нескольких manifest'ов (по одному на платформу), между которыми клиент сам
выбирает подходящий.

`rib` собирает image только под одну конкретную платформу за один запуск. При
`--from <registry-image>` он сам выбирает из index нужный вам manifest (по
`--platform`) и работает дальше с ним одним. На выходе `rib` тоже создаёт один
platform-specific manifest, а не новый index: OCI archive содержит
`index.json`, но с единственной ссылкой на собранный manifest.

## Зачем два разных хеша: `digest` и `diff_id`

У каждого сжатого слоя есть не один, а два SHA-256 идентификатора, и путать
их нельзя:

```text
diff_id = sha256(layer.tar)      — хеш НЕСЖАТОГО содержимого
digest  = sha256(layer.tar.gz)   — хеш СЖАТЫХ байт, которые реально передаются
```

Разница на практике: один и тот же несжатый tar можно сжать разными
инструментами или с разным уровнем компрессии — байты `.tar.gz` при этом
изменятся, а значит изменится и `digest`. Но развёрнутое содержимое
(`diff_id`) останется тем же самым. Поэтому:

- `digest` — то, что реально хранится и передаётся по сети (registry и OCI
  archive адресуют blob по нему), он записывается в
  `manifest.layers[i].digest`;
- `diff_id` — то, что описывает распакованный результат, он записывается в
  `config.rootfs.diff_ids[i]`.

Перепутать эти два значения — классическая ошибка при написании собственного
OCI-инструмента (образ будет выглядеть валидным, но не пройдёт проверку
целостности у некоторых клиентов).

Config и manifest тоже адресуются по содержимому — тем же способом:

```text
config_digest   = sha256(байты config.json)
manifest_digest = sha256(байты manifest.json)
```

Отсюда следствие, которое стоит держать в голове: если поменять любые
метаданные (например `--label`), то:

```text
изменятся байты config → 
изменится `config_digest` → 
изменится descriptor config внутри manifest → 
изменится `manifest_digest`
```

Итоговый digest — это как бы отпечаток *всего* image
целиком, включая метаданные, а не только файлов внутри него.

## Итог: image — это неизменяемый граф ссылок

Если собрать всё вместе, получится такая картинка:

```text
tag ───────► manifest digest или image index digest
                  │
                  ├──► manifest ─► config descriptor ──► config JSON
                  │                    │
                  │                    └──► ordered layer descriptors
                  │                                      │
                  │                                      └──► compressed layer blobs
                  └──► image index ─► platform-specific manifest descriptors
```

Ключевая идея, которая объясняет, как работает сборка в `rib`: существующие
объекты никогда не переписываются. Сборка — это всегда создание *нового*
корня графа: `rib` берёт descriptors базовых слоёв как есть, добавляет к ним
новые, собирает новый config и новый manifest — а старые blobs остаются
нетронутыми.
